Part 1The exam, and how to beat it

1.1 What you are walking into

The CKA is entirely performance-based. There is no multiple choice. You get a browser-based Linux desktop with a terminal and a handful of real clusters, and a list of tasks that each require you to change cluster state. A grader re-runs against those clusters afterwards — much like the validate.bash scripts in this repo.

Multiple clustersEvery task begins with a context-switch command. Running the right answer on the wrong cluster scores zero.

Spending 25 minutes on a stubborn NetworkPolicy in the first half hour. Two easy 4-point tasks at the bottom of the paper go untouched, and you finish at 61%. The grader does not care how hard a question was — only whether the end state matches. Skipping is a skill. Practise it in exam mode.

1.4 Rules you should never break in the exam

  • Switch context first, every single task. The task statement gives you the command. Copy it, run it, then read the task again.
  • Read the exact names. Namespace, object name, port, path. Graders match strings. pod-reader is not podreader.
  • Verify the end state, not your command. kubectl apply succeeding proves the YAML parsed, not that the pod runs. Always follow with a get or rollout status.
  • Never delete something you were told to fix. Several labs here (61, 70, 74) explicitly grade you on not deleting the object.
  • Leave the cluster tidy. Uncordon what you drained, unless told otherwise. Question 24 loses marks precisely there.

2.2 When there is no generator: kubectl explain

Roughly a third of exam objects (PV, StorageClass, NetworkPolicy, HPA behaviour, StatefulSet volume templates) have no kubectl create generator. You have two legitimate sources: the docs tab, and explain. explain is usually faster.

k explain statefulset.spec.volumeClaimTemplates

3.1 RBAC — the mental model that makes it easy

Two axes, and only two. Get these straight and RBAC stops being guesswork:

Role (namespaced)ClusterRole (cluster-scoped)
RoleBinding
(namespaced)		Permissions apply in that one namespace.The trick most people miss: the verbs apply only in the RoleBinding's namespace. One ClusterRole, reused in many namespaces, with no cluster-wide grant.
ClusterRoleBindingNot valid.Permissions apply in every namespace and to cluster-scoped resources.
A ClusterRole defines WHAT. The binding decides WHERE.

Lab 23 is built on exactly this: a ServiceAccount in finance must also list pods in hr, without a second Role and without cluster-wide access. The answer is a ClusterRole bound with a RoleBinding in hr. Reaching for create clusterrolebinding there grants the verb in every namespace and fails the negative check.

# Build it imperatively — faster and less error-prone than YAML
k create role pod-reader -n finance --verb=get,list,watch --resource=pods,configmaps
k create rolebinding report-runner-read -n finance \
    --role=pod-reader --serviceaccount=finance:report-runner

# Same ClusterRole, scoped to one namespace by the binding
k create clusterrole pod-lister --verb=list --resource=pods
k create rolebinding report-runner-hr-read -n hr \
    --clusterrole=pod-lister --serviceaccount=finance:report-runner

# VERIFY — including the negatives. This is how the grader thinks.
SA=system:serviceaccount:finance:report-runner
k auth can-i list pods      -n finance --as=$SA    # yes
k auth can-i get configmaps -n hr      --as=$SA    # no  <- the mark
k auth can-i delete pods    -n finance --as=$SA    # no  <- the mark
k auth can-i --list         -n finance --as=$SA    # everything this identity can do
The four RBAC bugs that appear over and over (Lab 59 has three of them)
  1. Singular resource name. resources: ["pod"] silently matches nothing. It is always plural: pods, deployments, configmaps.
  2. Wrong apiGroup. Pods, Services, ConfigMaps and Secrets are in the core group: apiGroups: [""]. Deployments, ReplicaSets, DaemonSets and StatefulSets are in apps. Getting this wrong is the #1 cause of a "correct-looking" Role that denies everything.
  3. Subject namespace. In a RoleBinding, a ServiceAccount subject needs its own namespace: field. It does not inherit the binding's namespace.
  4. Missing verb. list does not imply get, and neither implies watch. Grant all three when asked for all three.

Aggregated ClusterRoles (Lab 65)

A ClusterRole with an aggregationRule has empty rules — the controller fills them in by selecting other ClusterRoles by label. Do not write rules into the aggregate; if you do, they get overwritten.

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata: { name: monitoring-admin }
aggregationRule:
  clusterRoleSelectors:
    - matchLabels: { rbac.cka.local/aggregate-to-monitoring: "true" }
rules: []          # populated automatically — verify with: k get clusterrole monitoring-admin -o yaml

3.2 Onboarding a user: CSR → certificate → kubeconfig (Lab 66)

A five-step pipeline that appears in some form on most exams. The certificate CN becomes the username and each O becomes a group. Kubernetes has no User object — authorisation is attached to that CN by a binding.

# 1. Key + CSR.  CN = username, O = group
openssl genrsa -out dev-user.key 2048
openssl req -new -key dev-user.key -subj "/CN=dev-user/O=dev-team" -out dev-user.csr

# 2. Submit it. NOTE base64 -w0 — line wrapping breaks the request field.
cat <<EOF | k apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata: { name: dev-user }
spec:
  request: $(base64 -w0 < dev-user.csr)
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 86400
  usages: ["client auth"]
EOF

# 3. Approve and extract
k certificate approve dev-user
k get csr dev-user -o jsonpath='{.status.certificate}' | base64 -d > dev-user.crt

# 4. Authorise — namespace-scoped, using a built-in ClusterRole
k create rolebinding dev-user-edit --clusterrole=edit --user=dev-user -n dev-ns

# 5. Build a self-contained kubeconfig (--embed-certs makes it portable)
KC=dev-user.kubeconfig
SERVER=$(k config view --minify -o jsonpath='{.clusters[0].cluster.server}')
k config view --raw --minify --flatten \
  -o jsonpath='{.clusters[0].cluster.certificate-authority-data}' | base64 -d > ca.crt
k config set-cluster kubernetes --kubeconfig=$KC --server=$SERVER \
    --certificate-authority=ca.crt --embed-certs=true
k config set-credentials dev-user --kubeconfig=$KC \
    --client-certificate=dev-user.crt --client-key=dev-user.key --embed-certs=true
k config set-context dev@k8s --kubeconfig=$KC --cluster=kubernetes --user=dev-user --namespace=dev-ns
k config use-context dev@k8s --kubeconfig=$KC

k --kubeconfig=$KC get pods -n dev-ns          # works
k auth can-i list namespaces --as=dev-user     # no
Traps

Forgetting --embed-certs=true produces a kubeconfig full of file paths that break the moment it is moved. And a ClusterRoleBinding to edit grants cluster-wide edit — read whether the task says "in namespace X".

3.3 etcd backup and restore (Lab 73) — the highest-value 8 minutes you can rehearse

Almost guaranteed to appear. It is pure procedure, and the marks are all-or-nothing. Rehearse it until you can do it without the docs.

# STEP 0 — never memorise the paths. Read them off the static pod manifest.
grep -E "listen-client-urls|trusted-ca-file|cert-file|key-file|data-dir" \
     /etc/kubernetes/manifests/etcd.yaml

# STEP 1 — snapshot
export ETCDCTL_API=3
etcdctl snapshot save /opt/etcd-backup.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# STEP 2 — verify (snapshot status needs NO certs; it reads the file)
etcdctl snapshot status /opt/etcd-backup.db --write-out=table

# STEP 3 — restore into a NEW directory. Never restore over the live data dir.
etcdctl snapshot restore /opt/etcd-backup.db --data-dir=/var/lib/etcd-restore

# STEP 4 — point the static pod at the restored dir.
#          Change the hostPath on the HOST side only; the mountPath stays.
vim /etc/kubernetes/manifests/etcd.yaml
#   volumes:
#     - name: etcd-data
#       hostPath:
#         path: /var/lib/etcd-restore     <- was /var/lib/etcd

# The kubelet restarts etcd on manifest change. Force it if slow:
mv /etc/kubernetes/manifests/etcd.yaml /tmp/ && sleep 10 && mv /tmp/etcd.yaml /etc/kubernetes/manifests/
crictl ps | grep etcd

# STEP 5 — verify: pre-backup data is back, post-backup data is gone
k get nodes
k get cm -n <ns>
Expect a scary gap

While etcd restarts, kubectl returns connection refused for 30–90 seconds. That is normal. Wait and re-check rather than "fixing" something that is not broken. If it never comes back, crictl ps -a | grep etcd then crictl logs <id> — usually a permissions or path typo in the manifest.

3.4 Upgrading a cluster with kubeadm (Lab 24)

Order is everything, and the last step is the one people forget.

kubeadm upgrade plan                      # 0. what can we go to? Pick the next PATCH, never skip a minor.
TARGET=v1.32.2

apt-mark unhold kubeadm                   # 1. kubeadm binary FIRST
apt-get update && apt-get install -y kubeadm=${TARGET#v}-1.1
apt-mark hold kubeadm
kubeadm version                           #    confirm before continuing

kubeadm upgrade apply $TARGET -y          # 2. control plane (on a 2nd CP node: kubeadm upgrade node)

k drain <node> --ignore-daemonsets        # 3. drain BEFORE touching the kubelet

apt-mark unhold kubelet kubectl           # 4. kubelet + kubectl
apt-get install -y kubelet=${TARGET#v}-1.1 kubectl=${TARGET#v}-1.1
apt-mark hold kubelet kubectl
systemctl daemon-reload && systemctl restart kubelet

k uncordon <node>                         # 5. <-- THE STEP THAT LOSES MARKS
k get nodes                               #    Ready, new version, NOT SchedulingDisabled
Version skew, in one line

The kubelet may trail the API server, but must never lead it. That is the whole reason the control plane is upgraded before the kubelet — and why you upgrade one minor version at a time. On worker nodes the middle step is kubeadm upgrade node, not upgrade apply.

3.5 Certificates (Lab 68)

kubeadm certs check-expiration > /tmp/exam/before.txt   # full overview, all certs
kubeadm certs renew apiserver                          # renew ONE cert, not 'renew all'
openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -dates   # independent proof

If a task says "renew only X", kubeadm certs renew all is a wrong answer even though the cluster still works. Read the verb, then read the scope.

3.6 Static pods (Lab 67)

A static pod is owned by the kubelet, not the API server. The kubelet watches staticPodPath (confirm with grep staticPodPath /var/lib/kubelet/config.yaml; on kubeadm it is /etc/kubernetes/manifests) and creates a read-only mirror pod named <name>-<nodename>, owned by the Node object.

The consequence you must internalise

kubectl delete pod on a mirror pod does nothing lasting — the kubelet recreates it in seconds. Only removing the manifest file truly deletes it. This is also why every control-plane repair in Part 7 is done by editing a file on disk, never with kubectl.

The Argo CD trap (Lab 2)

--skip-crds does not reliably suppress CRDs. Many charts ship CRDs as ordinary templates gated by a chart value — for argo-cd it is --set crds.install=false. 3.8 Kustomize (Labs 37, 71)

# overlays/production/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

  - { name: api, count: 3 }

Three Kustomize traps

(1) patches.target matches the pre-prefix name. (2) Generated ConfigMaps/Secrets get a hash suffix — prod-app-secret-9t2bkm74hc — so never hard-code the generated name elsewhere. (3) Newer kustomize prefers labels: over the deprecated commonLabels:; both still apply cleanly.

The fastest marks on the paper. Most of these tasks are 2–4 minutes with a generator and one edit — which is exactly why you must not lose them.

4.1 Resource requests and limits — the calculation task (Labs 4, 19)

A recurring exam pattern: "divide the node's resources evenly across N replicas." It looks like a maths trap; it is actually a two-command lookup plus a formula.

k describe node | grep -A6 "Allocatable:"        # the numerator
k describe node | grep -A10 "Allocated resources" # what is already spoken for
The formula

per-pod request = (allocatable − system overhead) ÷ replicas, then round down.
System overhead is kube-proxy, CoreDNS and friends — budget ~150m CPU / ~250Mi on a small node, ~600m on a 3-CPU exam node. Memory in Ki ÷ 1024 = Mi. CPU: 1 core = 1000m.

Worked example — 1 CPU / 1800Mi node, 3 replicas: CPU (1000 − 150) ÷ 3 ≈ 283m → use 250m. Memory (1800 − 250) ÷ 3 ≈ 516Mi, but the existing limit is 500Mi → use 300Mi.

Three things that sink this question
  1. Requests must never exceed limits. If your computed request is above the existing limit, drop below the limit — do not raise the limit unless told to.
  2. Count containers, not pods. Lab 4 has 3 pods × 2 co-located containers = 6 consumers. Init containers run before the main container, so they do not add to the concurrent total, but the task may still require identical values on both.
  3. Only requests drive scheduling. Limits and actual usage are irrelevant to whether a pod is Pending.
# Fastest edit path — no YAML at all
k -n ns set resources deployment/wordpress --containers=wordpress \
    --requests=cpu=250m,memory=300Mi
k -n ns set resources deployment/web --limits=cpu=500m,memory=512Mi

# Or patch in place (Lab 18) — note limits and requests are separate maps
k patch deployment resource-app -n patch-ns -p '{"spec":{"template":{"spec":{"containers":
  [{"name":"nginx","resources":{"limits":{"cpu":"500m","memory":"512Mi"}}}]}}}}'

Why a strategic-merge patch is safe on containers: the container list is merged by the name key, so naming the container preserves everything else about it. That is why you must always include "name":"nginx" — omit it and the patch is rejected or replaces the whole list.

4.2 Scheduling controls — pick the right tool

MechanismDirectionUse when
nodeSelectorPod → nodeSimple exact label match. Fastest to write.
nodeAffinityPod → nodeYou need operators (In, Exists, NotIn) or a soft preference.
Taint + tolerationNode → podThe node repels pods. A toleration is permission to land, not a guarantee of landing.
podAffinity / antiAffinityPod → podSpread or co-locate relative to other pods, via topologyKey.

# Taints (Labs 10, 32)
k taint node node01 PERMISSION=granted:NoSchedule
k taint node node01 PERMISSION=granted:NoSchedule-        # trailing '-' REMOVES it
k describe node node01 | grep -i taint

# The matching toleration
tolerations:
- key: "PERMISSION"
  operator: "Equal"
  value: "granted"
  effect: "NoSchedule"

# Tolerate EVERYTHING (DaemonSet pattern, Lab 47)
tolerations:
- operator: "Exists"

# Required node affinity (Lab 30)
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - { key: disk, operator: In, values: ["ssd"] }

# Anti-affinity: never two of these on one node (Lab 44)
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchExpressions:
        - { key: app, operator: In, values: ["demo"] }
      topologyKey: kubernetes.io/hostname
The three effects, and the one that surprises people

NoSchedule blocks new pods. PreferNoSchedule is a soft hint. NoExecute evicts pods that are already running. Applying NoExecute to a busy node during an exam task will move workloads you did not intend to move.

4.3 Manual scheduling and the Binding API (Lab 74)

Two different problems with two different answers — and knowing which is which is the whole question.

# Pod does NOT exist yet -> spec.nodeName skips the scheduler; the kubelet just takes it
spec:
  nodeName: node01
  containers: [ { name: nginx, image: nginx:1.25 } ]

# Pod ALREADY exists -> nodeName is immutable. POST a Binding — literally what
# kube-scheduler does internally. This preserves the pod's UID and schedulerName.
k create -f - <<EOF
apiVersion: v1
kind: Binding
metadata: { name: orphan-pod, namespace: manual-sched }
target: { apiVersion: v1, kind: Node, name: node01 }
EOF
Why this appears on the exam

It proves you understand that scheduling is just writing a node name into the pod object. A pod requesting a schedulerName that does not exist will stay Pending forever with no FailedScheduling event at all — the absence of events is the diagnostic clue.

4.4 Deployments, rollouts and rollbacks (Lab 43)

k set image deployment/app-v1 nginx=nginx:1.20        # trigger a rollout
k rollout status deployment/app-v1                   # ALWAYS wait — this is your proof
k rollout history deployment/app-v1 > /tmp/exam/rollout-history.txt
k rollout history deployment/app-v1 --revision=2     # what changed in one revision
k rollout undo deployment/app-v1                     # back one revision

Part 5  ·  10% of the examStorage

The smallest domain, but it has the most precise failure modes. Storage questions are rarely about writing YAML — they are about understanding why a PVC will not bind.

5.1 The binding rules — memorise these five

A PVC binds to a PV only when all of the following hold. Lab 61 breaks three of them at once.

#RuleWhat "not matching" looks like
1storageClassName matches exactlyPV says manual, PVC says fast → Pending forever. Empty string "" means "no class" and is not the same as omitting the field.
2accessModes are satisfiedPVC asks for ReadOnlyMany, PV only offers ReadWriteOnce → no bind.
3PV capacity ≥ PVC requestA 1Gi PV can never satisfy a 5Gi claim. The reverse is fine — you just waste space.
4volumeMode matchesFilesystem vs Block. Rarely tested, instantly fatal.
5The PV is AvailableA Released PV (its old claim was deleted, reclaimPolicy Retain) will not re-bind until the stale spec.claimRef is cleared.
Lab 61's real lesson: order of operations

PVC spec fields (storageClassName, accessModes, resources.requests) are immutable. To fix a wrong PVC you must recreate it — but pvc-protection blocks deletion while a pod is using it, so the delete hangs. The sequence is:

# 1. pod first  2. then the PVC  3. then recreate both
k delete pod data-consumer -n ns
k delete pvc data-claim   -n ns
k apply -f fixed-pvc-and-pod.yaml
k get pvc data-claim -n ns          # Bound

StatefulSet volumeClaimTemplates (Lab 33)

A StatefulSet gives each replica its own PVC, named <template>-<statefulset>-<ordinal> — e.g. www-web-0. Note that volumeClaimTemplates is a sibling of template, not inside it, and that serviceName must name a headless Service or the per-pod DNS records never appear.

spec:
  serviceName: web-svc            # must be a headless Service (clusterIP: None)
  replicas: 3
  template: { ... }
  volumeClaimTemplates:           # SIBLING of template, not a child
  - metadata: { name: www }
    spec:
      storageClassName: cold
      accessModes: [ ReadWriteOnce ]
      resources: { requests: { storage: 1Gi } }
Deleting a StatefulSet does not delete its PVCs.

That is by design — the data outlives the workload. If you recreate the StatefulSet, it re-attaches the existing claims. Clean-up is manual: k delete pvc -l app=web.

Gateway API splits Ingress into two objects with separate ownership: the Gateway (infrastructure — listeners, ports, TLS) and the HTTPRoute (application — hostnames, paths, backends). Migrating an Ingress means reading its host, TLS secret and backend, then re-expressing them across the two.

kind: Gateway                     # apiVersion: gateway.networking.k8s.io/v1
spec:

      tls: { mode: Terminate, certificateRefs: [ { kind: Secret, name: web-tls } ] } }
---
kind: HTTPRoute

    backendRefs: [ { name: web-service, port: 80 } ]

6.4 NetworkPolicy — think in four questions

The four-question method
  1. Which pods am I protecting? → podSelector (empty {} = all pods in the namespace).
  2. Which direction? → policyTypes: [Ingress], [Egress], or both.
  3. Who is allowed? → from: / to: with podSelector, namespaceSelector or ipBlock.
  4. On which ports? → ports: with protocol.
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: db-policy, namespace: networking }
spec:
  podSelector: { matchLabels: { role: db } }      # 1. protecting
  policyTypes: [ Ingress ]                        # 2. direction
  ingress:
  - from:
    - podSelector: { matchLabels: { role: frontend } }   # 3. who
    ports:
    - { protocol: TCP, port: 3306 }               # 4. ports
The five NetworkPolicy traps
  1. Policies are additive; there is no deny rule. You cannot "override" a default-deny — you add allow policies alongside it. Union of all matching policies wins (Lab 58).
  2. Listing a policyType with no rules means deny-all for that direction. That is how default-deny is written.
  3. An egress policy blocks DNS. Port 53 UDP and TCP to kube-dns must be allowed explicitly, or the pod cannot even resolve the service name it is allowed to reach. This is the most common silent failure.
  4. The YAML dash matters enormously.
    - namespaceSelector: {…}
      podSelector: {…} = pods matching both (AND).
    - namespaceSelector: {…}
    - podSelector: {…} = either (OR). One character changes the security posture.
  5. Nothing is enforced without a policy-capable CNI. Flannel alone ignores NetworkPolicy entirely; Calico enforces it (Lab 8).
# The DNS egress rule you will need again and again
egress:
- to:
  - namespaceSelector: {}
    podSelector: { matchLabels: { k8s-app: kube-dns } }
  ports:
  - { protocol: UDP, port: 53 }
  - { protocol: TCP, port: 53 }

CoreDNS is configured by the coredns ConfigMap in kube-system, which holds a Corefile. Two plugin lines account for almost every DNS task:

7.3 Playbook C — Service returns nothing

Work outward from the pod. Four checks, in this order, and stop at the first that fails.

# 1. Are the pods actually Ready? A non-Ready pod is never an endpoint.
k get pods -n <ns> -l <selector>

# 2. THE decisive command. Empty endpoints = selector/label mismatch. Populated = a port problem.
k get endpoints <svc> -n <ns>

# 3. Compare the two strings character by character
k get svc <svc> -n <ns> -o jsonpath='{.spec.selector}{"\n"}'
k get pods -n <ns> --show-labels

# 4. targetPort must equal the container's real listening port
k get svc <svc> -n <ns> -o yaml | grep -A4 ports
k get deploy <d> -n <ns> -o jsonpath='{.spec.template.spec.containers[0].ports}'

# 5. Prove it end to end from inside the cluster
k run tmp --rm -it --image=busybox:stable --restart=Never -- wget -qO- http://<svc>.<ns>:80
Endpoints is the fork in the road

No endpoints → the Service selector does not match the pod labels, or no pod is Ready.
Endpoints present but no response → wrong targetPort, the app is not listening, or a NetworkPolicy is dropping the traffic.
Lab 56 packs four bugs into this one flow: bad image, wrong probe path, misspelt selector (app=webstack vs app=web-stack) and wrong targetPort. Fix them layer by layer — do not try to see all four at once.

Four habits that make this playbook reliable
  1. Back up before you edit: cp /etc/kubernetes/manifests/x.yaml /tmp/x.yaml.bak. A typo in an apiserver manifest takes the cluster away from you entirely.
  2. Wait 30–60 seconds after saving. The kubelet's re-sync is not instant. People "fix" a correct manifest twice because they checked too early.
  3. Look for the referenced file existing. Most of these faults are a path that points at nothing: controller-manager-missing.conf, scheduler-wrong.conf. Compare against ls /etc/kubernetes/.
  4. crictl is your fallback shell. crictl ps -a, crictl logs <id>, crictl pods. When the API server is down, this is the only way to see what the container actually said.

10.3 Exam-day checklist

  • Set up alias k, completion, $do, and ~/.vimrc before task 1.
  • Open the kubernetes.io docs tab and leave it open.
  • Run the context-switch command on every single task.
  • Re-read the task after finishing it. Names, namespaces, ports, file paths.
  • Flag and skip anything you cannot start in 60 seconds.
  • Back up any file under /etc/kubernetes/manifests/ before editing it.
  • After a control-plane edit, wait 30–60 seconds before judging it.
  • Uncordon anything you drained.
  • Confirm rollouts with rollout status, not with apply succeeding.
  • Keep 15–20 minutes for a verification pass over everything.
  • Never leave a task blank — a partial object scores more than nothing.
The last thing to remember

You need 66%, not 100%. Three complete, verified tasks are worth more than five half-finished ones. Move fast, verify hard, and let the difficult question go.
